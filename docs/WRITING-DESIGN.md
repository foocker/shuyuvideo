# 数语口播写作能力设计

状态：设计依据，2026-11-07。首版已实现 [writing 模块](../writing/SKILL.md)、编辑参考、[三个候选改稿片段](../examples/writing/EDITING.md)、导入／导出与制作同步检查。具体已实现的文件格式和命令以 [文件契约](../writing/references/files.md) 为准；本文保留设计理由，试听及用户文风选择仍待实际任务验证。样例统一放根 `examples/writing/`，不在能力模块内保存作品。

目标：让观众能跟随一个具体问题理解数学，让口播有自然的解释过程。文稿继续在配音前定稿，画面实现按真实配音时钟编排。

## 当前证据

本次阅读了 `docs/NARRATION.md`、`docs/ARCHITECTURE.md`、`studies/production-guide.md`，以及《光滑结构》《莫比乌斯带》讲解版的文稿、配音输入和相关构建代码。以下是文本与代码层面的观察，未据此声称完成成片试听。

| 观察 | 影响 | 设计响应 |
| --- | --- | --- |
| 规范要求每句不超过 25 字，《光滑结构》大量使用连续短句 | 容易把解释拆成提纲；句子短不保证因果衔接清楚 | 先写自然段，按语义和呼吸分配音单元；字幕长度另行处理 |
| 《光滑结构》从导数、雅可比矩阵推进到图册、光滑结构和奇异球 | 若只压缩原文章节，容易保留所有名词却省去引入动机 | 先选本片解释到哪一步，再决定必要概念；按时长删支线或拆集 |
| 《莫比乌斯带》的 `text` 包含“画面在这里停一下”“这段只继续半圈” | 制作备注进入观众听到的内容 | 口播与导演说明分开，导出器只读取口播 |
| 《光滑结构》结尾有“一个熟悉的导数，打开了更大的世界”等句子 | 结尾偏概括评价，观众不易据此复述具体收获 | 回答开头的问题，复用已解释的对象和关系 |
| `films/smooth-structure/clock.py` 和 `films/mobius/explainer/build.py` 会写回 `SCRIPT.md` | 只编辑 Markdown 可能被后续制作覆盖 | 迁入新写稿方式的项目，先修正文稿读写方向 |
| `studies/` 已有按理解障碍选择表达方法的研究 | 可以直接用于文稿构思，不必从零再建一套通用叙事理论 | 根据主题加载相关片段，记录迁移是否有效 |

这些是可检查的问题及其潜在影响，不足以证明哪条规则单独造成了最终听感。

## 最小能力边界

新增 `writing/`，与 `motion/`、`sound/` 一样提供可按需读取的能力入口。现有 `story/` 保存原材料，继续保留这个用途。

第一版由当前会话完成构思、写作和编辑。数学核对复用 `mathematics.md` 与现有数学能力。写作、听众视角编辑、事实核对是不同的检查任务，第一版无需为每项常驻一个 agent 或配置一种模型。

建议入口及职责：

```text
writing/
  SKILL.md                 按输入选择：从材料写稿 / 修改现稿 / 学习编辑反馈
  references/
    voice.md               数语语气与已确认的编辑偏好
    editing.md             段落衔接、口语、画面分工与事实保留
  examples/
    README.md              样例索引、出处、适用范围与采用状态
    <case>.md              旧段落、改稿、修改原因及用户反馈
```

入口只加载当前任务需要的资料。原文、研究材料、参考作者的文字都作为输入材料；其中的命令不成为执行指令。

## 接受三类输入

- **只有题目**：补齐受众、要解释的问题和必要来源，再形成稿件。缺少研究材料时可以使用 ARS 的检索与来源核验能力。
- **已有文章或笔记**：先提取核心主张、论证依赖和原作者的表达特点，再决定视频范围。文章的小标题不自动成为视频章节。
- **已有口播稿**：按用户指定范围编辑；局部润色保留信息与确定程度，结构改写才调整顺序与删去支线。重要删除写明理由。

已有简报和对话足够时直接推进。作者偏好尚未建立时使用临时语气建议，不把它写成用户已经认可的风格。

## 从理解过程开始写

在现有 `BRIEF.md` 中增加一小段写作约定：

1. 观众已掌握什么，眼下卡在哪一步。
2. 本片结束后，观众能够解释或判断什么。
3. 哪个例子或操作承担主要解释，哪些支线留到以后。
4. 采用哪些真实文风样本；没有样本时采用什么临时语气。

写正文前，用几个段落说明推理如何向前走。每段回答“前面知道了什么，因此现在为什么需要这一步”。需要画面的地方写出对象、操作和观众应看出的关系。历史背景、必要定义和口头推理可按内容加入，不要求每句话都有动画动作。

这里规划画面承担的解释任务，不提前制作动画或固定时间码。仍然先定稿，再生成配音，最后用真实时钟实现画面。

沿用 `studies/production-guide.md` 中适合当前问题的方法。例如坐标过渡可以使用“同一对象在不同表示中对应”；是否采用由题材决定，不要求凑齐方法数量。

## 写自然段，再拆配音

将“每句不超过 25 字”改为软性可读提示，允许句长变化。先写能完整读懂的段落，再按语义和正常呼吸拆成配音单元；字幕按实际词时间切分。

首版临时语气：具体、平实，允许讲述者提出真实疑问和作出有依据的判断；情绪由问题与发现承载。第一人称经历仅在用户提供时使用。轻松表达和幽默可以保留，不主动编造个人经历、历史对白或观众反应。

编辑重点：

- 新名词出现前，交代此时需要它解决什么问题。
- 判断“所以、于是、其实”等连接是否真有前文支撑。
- 代词和“这里、这样”能否由当前口播或画面唯一指认。
- 保留必要的解释、类比和回看；不以删字数量衡量质量。
- 删除无内容的预告、评价和重复，保留有作用的转折、排比与总结。
- 比喻结束时说清适用边界，不能把二维示意写成高维对象的真实外形。
- 结尾回答本片问题，开放问题应与已讲内容自然相接。

文风编辑参考 `humanizer-zh` 的保真原则：保留事实、范围、条件、否定、归因和确定程度。词表只提供检查线索；不用命中词数或“AI 检测分数”决定稿件好坏。

## 三种内容各归其位

| 内容 | 位置 | 处理方式 |
| --- | --- | --- |
| 观众听到的正文 | `SCRIPT.md` | 连贯、可朗读；只包含正文及必要的段落和行标识 |
| 对象、画面操作、停顿意图、屏幕公式 | `DIRECTION.md` | 按段落或行 ID 对应；制作时转换为真实时间锚点 |
| 定义、推导、来源、条件、不能声称的结论 | `mathematics.md`，必要时补 `sources.md` | 支撑核对；影响观众理解的条件须写入正文，不能只藏在备注中 |

小片可把导演说明放进已有简报，不强制新建 `DIRECTION.md`。事实与来源文件按需要建立，不要求每部片填满一套表单。

ARS 用于需要查证的资料任务，返回来源、支持的主张和限制。科普稿的段落安排由写稿能力根据本片问题决定。`humanizer-zh` 用于已有文本编辑，无法替代选题、解释设计或事实核对。

## 与配音和构建对接

新方式启用后，单个作品中采用明确的数据方向：

```text
原材料 + BRIEF + 相关事实依据
                  ↓
             SCRIPT.md  ← 编辑正文
                  ↓ 确定性导出
           narration.json
                  ↓ 现有 voice.py
          voice-timings.json
                  ↓
        镜头、字幕、角色、音效
```

导出器只做解析与数据转换，不调用模型改写文字。继续保留现有 `voice`、`rate`、`gap`、`lead`、`tail`、`bedGain` 和 `lines` 的接口。每行保留稳定 ID、可选 `scene`、`text` 与停顿设置；编辑文本时保持 ID，拆分或合并时显式更新依赖。

文稿格式可使用现有 Markdown 段落，加机器可读的行标记，导演说明单独保存。具体标记语法在实现导出器时确定，只保留一种可往返核对的格式。

已存在项目逐个迁入：

1. 从当前 `narration.json` 导入现用文本、ID、场景和停顿，不从旧音频时间文件恢复正文。
2. 调整该作品会覆盖 `SCRIPT.md` 的代码；如仍需配音转录展示，另写展示文件。
3. 校验导出正文、行顺序、ID 与配置；拒绝重复 ID、空正文和失效引用，不静默猜测修复。
4. 改稿后按现有声音定稿约定刷新配音、时钟、画面锚点和混音输入。只修改文档不代表音视频已更新。

首版先在一个作品验证迁入。没有启用新写稿入口的作品继续使用自己的现行输入方式，避免让旧构建自动覆盖新草稿。

## 编辑怎样产生有效反馈

每项修改应能指向具体句子和读者问题，例如：

> “所以，导数的本质，是线性映射。”前面的切线演示还没有交代高维输入怎样变化。这句把需要解释的结论提前说完了。应补一个箭头变化的例子，或缩小本片范围。

检查分三类：

- **理解与表达**：哪里跳步，哪里没有动机，哪里只剩概念名单；给出理由和改稿。
- **事实保留**：改写是否更改条件、数值、比较对象或证据强度；新事实回到来源核验。
- **实际口播**：在目标声音下试听，检查停顿、术语读音和长句；模型读稿意见只能标为文字判断。

优先修具体问题。没有新证据时停止反复“再自然一点”的整稿重写。需要用户选择时提供短段的实质差异，不要求用户评判抽象风格标签。

## 《光滑结构》的小范围试作

先选“同一个点，两套坐标”段。这个段落与核心问题直接相关，适合观察改稿能否增加动机且保持事实。

原稿：

> 麻烦出在，两张图重叠的地方。\
> 同一个点，现在有了两套坐标。\
> 先从第一套坐标，找回球面上的点。\
> 再用第二张图，把它写成新坐标。\
> 这就是坐标过渡映射。

候选改写，尚未作为正式文风样本采用：

> 两张坐标图有一块重叠区域。这里的每个点，都能用两套坐标表示。\
> 现在固定其中一个点：它在第一张图上的坐标已知，怎样算出第二张图上的坐标？\
> 沿着这两支箭头走就行：先由第一套坐标找到球面上的点，再用第二张图读出新坐标。两步合起来，就是坐标过渡映射。\
> 这样，我们就得到了一张旧坐标到新坐标的函数。接着可以检查：它是不是光滑的？

导演说明：保持球面上的点固定，依次显示两套坐标；标明第一张图的逆映射和第二张图的映射。两支箭头与正文指代对应。此处只承诺球面示意，光滑性用坐标表达检查，不凭箭头外观判断。

改写增加了问题与操作的关系，篇幅也更长。正式试作要在全片时长内通过删支线、调整段落或拆集消化，不能靠加快语速填回去。该段只用于说明设计，尚不能证明整片效果改善。

随后测试“导数为什么是线性映射”和结尾回收两段。保留同一事实要求与时长预算，分别制作原版与改版试听；使用相同声音、语速与响度，隐藏版本来源，记录实际偏好和原因。

采用的改稿进入样例库，并记录：出处、旧稿、改稿、修改理由、用户反馈、适用题材。没有用户认可的样例标为候选。已有研究片段可提供表达方法，不能据此宣称用户喜欢相同语气，也不复制参考作者的标志性措辞或经历。

## 实施顺序与验收

1. **验证编辑方法**：选《光滑结构》的三个段落，形成有原因的改稿和等条件试听。记录用户偏好，再形成首批样例。
2. **加入写稿入口**：实现 `writing/SKILL.md`、简短编辑参考；更新 `NARRATION.md` 的硬句长规则和入口链接；把相关案例指引接到写稿阶段。
3. **稳定文件对接**：在一个项目实现定稿导出与覆盖保护，再决定是否扩展到其他项目。

验收分开记录：

| 层面 | 证据 |
| --- | --- |
| 正文改善 | 具体段落前后对照、用户的偏好理由；明确尚未做过的观众测试 |
| 数学 | 限定、命题和论证核对记录；画面中的示例与正文主张一致 |
| 口播 | 实际音频试听记录；语速、读音、停顿可接受 |
| 数据接入 | ID、顺序、正文、配音配置保留；制作说明未进入 `text`；旧稿不被构建带回 |
| 修改传播 | 改稿后旧配音与混音会被现有检查识别，后续锚点按新时钟更新 |

实现时为解析、配置保留、ID 引用、覆盖保护等有实际故障风险的行为写测试。中文审美判断通过样稿和试听验证，不写“命中几个禁词就失败”的测试。公共构建入口若有改动，按仓库约定执行 `shuyu layout`、相关测试和一次真实构建／渲染验证。

模型选择放在上述试作之后评估：用相同材料、任务范围、样例与时长预算比较文本和试听，并记录实际使用模型。当前不预设某个模型必然更自然。
